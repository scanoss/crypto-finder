Java callgraph contract coverage also includes post-quantum key encapsulation and signatures. For the JDK (21 onwards) it covers javax.crypto.KEM: getInstance, encapsulator and decapsulator creation, encapsulate, decapsulate, the Encapsulated result and its secret key, and NamedParameterSpec, whose name selects the algorithm (for example ML-KEM-768 or ML-DSA-65 on JDK 24). For Bouncy Castle it covers the lightweight ML-KEM (FIPS 203), ML-DSA and HashML-DSA (FIPS 204), SLH-DSA and HashSLH-DSA (FIPS 205) and LMS/HSS (RFC 8554) generators, extractors, signers, key-pair generators, key-generation parameters and key objects under both package layouts: org.bouncycastle.pqc.crypto in 1.79 to 1.85 and org.bouncycastle.crypto from 1.84 (LMS/HSS from 1.65, relocated in 1.86), and the provider-side MLKEMParameterSpec, MLDSAParameterSpec and SLHDSAParameterSpec lookups by name, KEMGenerateSpec, KEMExtractSpec and KEMParameterSpec with their builders, the ML-KEM and ML-DSA key specs, and the LMS key-generation specs. Encapsulation, decapsulation, signing and verification are reported as operations; the algorithm name or parameter-set argument is exposed as a parameter role. The static parameter-set fields (MLKEMParameters.ml_kem_768, MLDSAParameterSpec.ml_dsa_65, ...) are matched by the detection rules rather than by contracts.
