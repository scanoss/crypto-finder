The model

Detection first. Context second.

A scan identifies terminal cryptographic operations. Structural analysis then connects findings to functions, callers, dependency context, and nearby lifecycle calls when the source permits it.

Inputs. The source tree, rules sources, language settings, exclusions, and cache policy define what the run can see.
flow.txt
source tree + rules
      |
      +--> terminal operations --> interim JSON / CycloneDX CBOM
      |
      +--> source relationships --> reachability export
BoundaryReachability is static source evidence. It helps direct a review. It does not execute the application or prove that a path occurs at runtime.

Why keywords are not enough

A word such as encrypt can appear in a comment, variable name, documentation block, or unrelated text. Keyword-only search creates noisy false positives and misses the difference between setup code and a terminal operation.

Why context-aware rules help

Rules inspect source structure and surrounding syntax to identify the cryptographic operation itself, then attach metadata to that evidence. Detection stays focused on terminal operations instead of turning every nearby call into a finding.

Why reachability is separate

Detection answers what operation is present. Reachability answers how a static caller path may connect to it. Keeping stages separate makes an isolated source match useful even when a path cannot be resolved.

What structure can and cannot show

Source positions, call relationships, type and contract knowledge, and available dependency source improve caller links. Dynamic dispatch, reflection, generated code, and missing source can leave caveats or unresolved paths.

Supporting contextLifecycle, configuration, factory, and output calls are derived from the same program structure around the finding. They explain how an object is used, but they are not separate cryptographic findings.
First run

Install once. Scan a real revision.

Use Go, build from source, or use a container. The default remote rules workflow keeps rule management separate from the source tree. Local rules are available for offline or controlled runs.

Install

shell
# Build from source
git clone https://github.com/scanoss/crypto-finder.git
cd crypto-finder
make build
sudo make install

# Or install with Go
go install github.com/scanoss/crypto-finder/cmd/crypto-finder@latest

Configure and scan

shell
# Configure the default remote rules workflow
crypto-finder configure --api-key YOUR_API_KEY

# Retain detailed interim JSON
crypto-finder scan --output findings.json ./service

# Local rules only
crypto-finder scan --no-remote-rules \
  --rules-dir ./rules ./service
Remote rules and cache policy

The remote rules cache is reused between scans. When an expired cache cannot be refreshed, the default workflow can use a recent stale copy. Use --strict when the run must fail instead of using stale rules. --no-cache forces a fresh download attempt.

Structured progress for integrations

Add --progress to emit immediate JSONL lifecycle events on stderr. Findings stay on stdout or in --output, and human logs are suppressed. The stream reports scan, rules, detection, optional dependency and export phases, and callgraph work only when it runs. Terminal failures use the existing structured JSON error payload; an explicit --error-format=text cannot be combined with progress mode.

shell
crypto-finder scan --progress \
  --output findings.json ./service

# stderr: one JSON object per lifecycle transition
{"event":"scan_progress","schema_version":"1","phase":"scan","status":"started"}
Useful first-run flags

--output retains the findings report, --format cyclonedx writes a CBOM, --fail-on-findings returns a non-zero result when findings exist, and --scan-dependencies includes resolved third-party source. File exports create missing parent directories and replace existing files only after a complete write.

Configuration precedence

For access settings, a command-line value overrides the environment, and the environment overrides persisted configuration. The supported environment variables are SCANOSS_API_KEY and SCANOSS_API_URL.

Stop a running scan

Use Ctrl+C to cancel an active scan. Crypto Finder stops its scan subprocesses and returns a structured scanner_canceled error, including when dependency scanning is enabled; it does not emit a partial dependency report. Timeouts continue to return their timeout error.

Source fixtures

Look for the terminal operation.

These compact examples show the kind of source expression a finding anchors. They are review fixtures, not recommendations for key management, nonce policy, or application design.

go
func Seal(key, nonce, plaintext []byte) ([]byte, error) {
    block, err := aes.NewCipher(key)
    if err != nil { return nil, err }
    gcm, err := cipher.NewGCM(block)
    if err != nil { return nil, err }
    return gcm.Seal(nil, nonce, plaintext, nil), nil
}

Review the matched call, metadata, and any caller path. Do not infer key origin or nonce policy from this excerpt.

java
public byte[] encrypt(byte[] plaintext, SecretKey key) throws Exception {
    Cipher cipher = Cipher.getInstance("AES/GCM/NoPadding");
    cipher.init(Cipher.ENCRYPT_MODE, key);
    return cipher.doFinal(plaintext);
}

The finding may describe the algorithm and operation separately. Read the source line and metadata together.

python
from cryptography.fernet import Fernet

def encrypt(key: bytes, plaintext: bytes) -> bytes:
    return Fernet(key).encrypt(plaintext)

A compact match is still only one piece of evidence. Check the surrounding function and how the result is used.

Review tipA finding identifies source evidence. It is not, by itself, a security verdict or a statement about runtime exploitability.
Transitive code

When crypto lives below your module.

Dependency scanning resolves supported third-party packages, scans available source, and traces findings back through call relationships that can be built in the scan environment.

shell
# Scan application code and resolved dependencies
crypto-finder scan --scan-dependencies \
  --export-callgraph callgraph.json \
  --output findings.json ./service

# Select an ecosystem only when automatic detection is not suitable
crypto-finder scan --scan-dependencies \
  --dep-ecosystem java ./service

Supported ecosystems

Go, Java with Maven or Gradle, Python with pip, and Rust with Cargo.

Identity

Use source and dependency_info to distinguish direct code from dependency-backed findings. Known ecosystems also include an optional purl for package identity; it may be versionless when the dependency version is unavailable.

Coverage

Missing source, unavailable toolchains, and unresolved calls limit what can be attributed.

transitive path
application entry point
  -> service wrapper
     -> dependency helper
        -> terminal cryptographic call
Source requirementA dependency without usable local source cannot provide source-level finding evidence. Treat missing source as a coverage limitation, not as evidence that the dependency has no cryptography.
Static path

Follow the finding back to callers.

The callgraph export is separate from interim JSON. Join a record with finding_id, then read each chain from its first caller to the function containing the matched operation.

shell
crypto-finder scan \
  --export-callgraph callgraph.json \
  --output findings.json ./service
Finding explorer / one abbreviated record
src/service/token.go:18

func issueToken(secret []byte) string {
    digest := sha256.Sum256(secret)  // finding anchor
    return hex.EncodeToString(digest[:])
}

Start with the exact file, line, and matched expression. Then read the surrounding function.

These examples are synthetic and abbreviated. Exact field names and nesting depend on the artifact. finding_id joins the records; source, file, line, match, and metadata describe the evidence. Dependency-backed records may also include dependency_info with module, version, and an optional purl, which may be versionless when the dependency version is unavailable. Reachability exports can add call_chains, entry_call, crypto_call, and supporting_calls. If a link is incomplete, unresolved_reason and related caveats explain why. Treat every field as review evidence, not a runtime proof or policy verdict.

finding_id

Join key shared with the interim finding.

call_chains

Static path or paths from a reachable caller to the finding anchor.

entry_call

How execution entered the next function, including best-effort parameter provenance.

crypto_call

The matched crypto-relevant call at the end of a chain.

supporting_calls

Context and lifecycle calls derived from the same graph. They are not findings.

unresolved_reason

Why a finding could not be fully connected. Investigate rather than treating it as unreachable.

Evidence formats

Pick the artifact for the reader.

Keep interim JSON for detailed analysis. Use CycloneDX CBOM for standardized reporting. Add callgraph or graph fragment exports when structural context or reuse matters.

Go integrations can import pkg/schema for the interim report and pkg/failure for structured error payloads. Both preserve the documented JSON contract without requiring implementation-package imports.

Interim JSON

Detailed findings, source match, metadata, status, attribution, and finding_id. Format version is 1.6; direct assets may promote a canonical rule purl, while dependency-backed assets keep identity in dependency_info.purl.

CycloneDX CBOM

Standardized Cryptography Bill of Materials. The documented output is CycloneDX 1.6.

Structure exports

Finding-centric callgraph export uses schema 6.9 and carries an optional top-level purl for direct findings; dependency-backed records keep package identity in dependency_info.purl. Findings carry reachable when the scan included dependencies: true when user code reaches the crypto, false when it does not. The field is absent when a library is scanned on its own, since there is no user code to reach from. Reusable fragments use graph-fragment-1.9 and carry direct finding package URLs through annotations. Integration consumers must validate against the published schema matching the artifact version and fail closed when no matching schema exists.

shell / conversion

crypto-finder scan --format cyclonedx --output cbom.json ./service

# Convert an existing interim report
crypto-finder convert findings.json --output cbom.json
What not to infer from a CBOM

A CBOM is an inventory and interchange artifact. It does not describe runtime exploitability, application approval, or compliance by itself. Pair it with source review and the relevant policy.

Why keep both artifacts

Interim JSON keeps detailed source and finding context. CBOM keeps a standardized component representation for inventory and integration. They serve different readers.

Repeatable analysis

Rebuild structure only when it changed.

The call graph is the expensive structural part of a scan. Reuse a graph fragment with annotate when only the detection rules changed and the fragment still represents the same source.

source changed
crypto-finder scan --export-graph-fragment fragment.json ./service

Rebuild the structure after a source change. The new fragment belongs to that source revision.

rules changed
crypto-finder annotate \
  --import-fragment fragment.json \
  --source ./service --output annotation.json

Re-run detection against the imported structure when source did not change. The fragment metadata includes the graph algorithm version.

Do not reuse blindlyA graph fragment is a cache of source structure, not a substitute for scanning changed source. Rebuild it whenever the source changes.
Repeatable execution

Keep source read-only and outputs explicit.

Mount the source as read-only, write reports to a separate output directory, and provide credentials through environment-managed secrets.

docker
docker run --rm \
  -v "$PWD/code:/workspace/code:ro" \
  -v "$PWD/output:/workspace/output" \
  -e SCANOSS_API_KEY=YOUR_API_KEY \
  ghcr.io/scanoss/crypto-finder:latest \
  scan --output /workspace/output/findings.json /workspace/code

latest

Recommended standard image for a containerized source scan.

latest-slim

Binary-only image for environments that provide required tooling.

latest-deps

Use for dependency scanning. It includes the documented language toolchains.

CI gate

workflow excerpt
- name: Run Crypto Finder
  run: |
    docker run --rm \
      -v ${{ github.workspace }}:/workspace \
      -e SCANOSS_API_KEY=${{ secrets.SCANOSS_API_KEY }} \
      ghcr.io/scanoss/crypto-finder:latest \
      scan --output /workspace/results.json /workspace/src

- name: Gate on findings
  run: crypto-finder scan --fail-on-findings /workspace/src
CI policy choiceThe default cache behavior favors continuity. Use --strict when policy requires a fresh ruleset instead of stale-cache fallback.

Published container images use version-pinned toolchains and verify remote installer inputs before execution, keeping dependency scans reproducible across builds.

Review boundaries

Evidence is useful when its limits are visible.

A finding is strongest when the source, matched operation, metadata, and caller path are all available. It is never a runtime trace or an automatic approval decision.

Static analysis does not execute the application

Call relationships are built from available source and syntax. Reflection, dynamic dispatch, runtime-generated code, function values, macros, incomplete types, and unavailable source can reduce or prevent path resolution.

Dependency coverage is environmental

Dependency findings depend on resolved metadata, the required local toolchain, and source available in the scan environment. Missing source is not proof of no cryptography.

Language-specific resolution has limits

Java source archives and multi-module resolution are best effort. Python packages without usable source and dynamic dispatch are limited. Rust trait dispatch and macro-generated code are not fully represented.

Unresolved is not unreachable

When a record carries unresolved_reason, surface the reason and investigate. Do not convert a missing path into a claim that the operation cannot run.

Review a finding in order

  1. Confirm the target revision, rules source, cache policy, and whether dependency scanning was enabled.
  2. Read the file path, line range, matched expression, and metadata in interim JSON.
  3. Join the callgraph export with finding_id when caller context or parameter provenance matters.
  4. Read unresolved reasons, ambiguous edges, and missing dependency source as explicit caveats.
  5. Make the security or compliance decision with application context, not from a single static field.
Public-safe practiceKeep reports and review notes tied to source evidence. Do not present an inventory entry or static chain as a claim about runtime exploitability, approval, or compliance by itself.
