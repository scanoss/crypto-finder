- Bouncy Castle EC key generation now reports the curve's field size when the curve is named by a string literal. `ECNamedCurveTable.getByName("secp256r1")` (and the `SECNamedCurves`, `NISTNamedCurves`, `TeleTrusTNamedCurves` and `CustomNamedCurves` lookups) reports 256, and the size follows the `X9ECParameters` through `p.getCurve()`, `p.getG()`, `new ECDomainParameters(p)` or `new ECDomainParameters(curve, g, n[, h])` and `new ECKeyGenerationParameters(domain, random)` to `ECKeyPairGenerator.init(params)`. The JCA with the Bouncy Castle provider reports the same for `KeyPairGenerator.initialize(ECNamedCurveTable.getParameterSpec("secp384r1"))` and `initialize(new ECNamedCurveGenParameterSpec("secp256k1"))`. The size is the curve's field size, the same unit as `ECGenParameterSpec`, not the bit length of the group order that `ECKeyGenerationParameters.getStrength()` holds. A curve name that is not a literal, that the table does not list, or an object whose parts come from lookups of different curves reports no key length. (#716)
- A Java key size is now traced one more hop through local variables, so a size reaches a generator through a getter chain such as `p.getCurve()`; `source_nodes` of Java calls can nest one level deeper. When several key-size producers sit behind one argument and disagree, the call reports no key length instead of the first one found. (#716)
- A Java local or parameter that the method writes again after its declaration (plain, compound or `++`/`--` assignment, in any branch, loop or block) no longer gives its declaration's value as a source. `int n = 128; n = 256; kg.init(n)` and a reassigned `ECGenParameterSpec` used to report the first value; they now report no key length. (#716)
