- Java interface and abstract-class dispatch now links a call only to methods of real subtypes of the receiver's declared type. Before, a call whose target the graph could not find exactly was linked to every method with the same name and argument count under the same two-segment package root, so `TikaInputStream.get(File, Metadata)` reached `org.apache.cxf...JaxrsResponseFuture.get(long, TimeUnit)` and chained on through unrelated libraries to findings that no caller reaches.
- Subtypes for that dispatch come from the extends and implements clauses of the parsed sources, followed transitively and resolved through each file's imports. The bytecode type hierarchy is not consulted at this stage, because the call-graph build runs dispatch before it resolves types from bytecode. An ancestry that passes through a type only a jar defines therefore counts as incomplete, and the edge stays and reads `name_only`.
- A superclass method is still a dispatch target when some implementing subclass inherits it without overriding.
- An edge is dropped only when the candidate's whole ancestry is known and excludes the receiver type. When some ancestor's supertypes are not in the graph (an unindexed library base class, a language whose parser records no base classes), or a supertype's simple name is shared by several known types, the edge stays as before and its chain step reads `name_only`.
- The graph can still miss a subtype relation it has no record of at all, for example one that goes through a member type inherited from a supertype in an unindexed jar when a graph type of the same simple name sits in the caller's package, so a missing hierarchy can in rare cases still hide a path.
- Go interface dispatch links only types that declare every method of the interface. Methods promoted from an embedded field are not seen.
- A call on a class that inherits the method links, as exact edges, to every inherited declaration of that name and arity not overridden by a nearer class, so an overload declared further up stays reachable past a nearer overload. The edges then narrow by argument type. The Node parser now records `class Sub extends Base` clauses for this.
- An overloaded Java method is resolved by the static types of the call's arguments before any dispatch fallback. `tika.parseToString(stream)` with an `InputStream` argument links to `parseToString(InputStream)` only, not also to the `File`, `Path` and `URL` overloads. A Java type name counts as certain only when the source spells it fully qualified, or when the file declares no type parameter or local class of that name and at most one type of that simple name exists in the graph (source types including nested ones, and indexed bytecode types); Java's scoping is not modeled beyond that. An overload wins outright only when every argument's type is certain and equals its parameter type; otherwise every overload that accepts the known types is kept, except one that another accepted overload beats whatever the untyped arguments turn out to be (the same parameter types at the untyped positions, the exact types at the typed ones). Argument types come from declared variables, literals, string concatenation, constructors and the return type the graph records for a called method; an argument whose type the call site does not establish constrains nothing. An argument or parameter whose type is not certain, or whose class hierarchy is not fully in the graph, is assumed to fit, so it never rules an overload out. When no overload accepts the recorded types, all same-arity overloads are kept as before.
- `--export-callgraph` now fills `call_chains[].entry_resolution` and `entry_declared_type` in the local CLI export, as schema `6.13` defines them and the stitched export already did: `exact`, `interface_dispatch`, `python_subclass_dispatch` or `name_only` for how the call arriving at each frame was resolved, and the static type a dispatch expanded. A consumer can keep the certain part of a route and discount the rest. The schema version is unchanged.
