- `finding_graphs[].dependency` on the live and stitched callgraph exports (`graphfrag.ExportFindingDependency`): a dependency finding names the dependency it sits in (`module`, `version`, `purl`), whether the application depends on it `direct`ly or `transitive`ly (`relationship`), and its shortest route from the application in the resolved dependency graph (`path`, a direct dependency first and the finding's dependency last, each with `module`, `version` and `purl`). A route through dependencies parsed with source is preferred over a shorter one that is not. First-party findings carry no block, and the top-level `purl` still names the rule's library on first-party findings only. A module the resolution picks at more than one version, as npm does for conflicting ranges, is told apart by version on the live export: each copy has its own route, so the nested copy is not reported `direct` because another copy is. Where the resolver records no versioned edges, `relationship` and `path` are omitted for such a module and for any dependency whose route crosses one. Optional, and new in interned callgraph schema `6.17`.
- A dependency that joined the call graph without source code (a Java dependency with no source JAR, indexed for types only) is no longer silent. On a finding's `dependency.path` it carries `without_source: true`, and a dependency finding that no chain reaches, and whose every route from the application crosses such a dependency, reads `unknown` with `unresolved_reason: "dependency_without_source"` and `analysis.call_chains: "partial"` instead of `unreachable`, since its chain may run through calls the graph does not hold.
